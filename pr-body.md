This pull request addresses repeated external-mod authoring failures where new Fast64 models and behavior-heavy mods were frequently blocked by unsupported conversion macros, inconsistent texture state defaults, and a narrow data-driven runtime surface for items, actors, and scene behavior wiring.

From a user perspective, the previous behavior caused common mod packs to disable at startup, required frequent manual model cleanup, and limited creators to a small subset of interactions unless they dropped to custom WASM logic. The practical effect was slower iteration, fragile mod portability across assets, and frequent regressions in visual output (especially texture filtering and tile scaling edge cases).

The root cause was concentrated in the external mod pipeline and runtime boundary: conversion support did not cover several macros now common in Fast64 exports, unknown macro handling was too strict for non-structural state commands, and behavior/event/action coverage did not expose enough engine-side operations to keep workflows JSON-first.

This change expands the conversion and runtime stack in a compatibility-preserving way. The Fast64 path now includes broader macro handling and conservative texture/tile normalization behavior, while keeping hard failures for structurally unsafe constructs. Explicit model texture filter overrides remain deterministic (`point`/`bilerp`) and are applied consistently. On the runtime side, the behavior graph and actor/item action surface were expanded with additional triggers, conditions, and actions (including switch/event/inf flags and rupee economy actions), plus item cooldown/equip event hooks and behavior aliases for migration safety. Scene and behavior definition loading remains capability-gated and backward-compatible with existing API v1/v2 mods.

Validation was performed with a full Windows release build and the generated binary completed successfully. The main verification command used was `cmake --build build/x64 --config Release --target soh -- /m`, and the resulting `soh.exe` was produced without new build-blocking errors.

Overall, this PR is intended to reduce hard stops for new imported models, improve visual consistency for converted assets, and significantly widen data-driven mod creation freedom for custom items, actors/NPCs, and behavior-based scene logic while preserving compatibility for existing mods.
